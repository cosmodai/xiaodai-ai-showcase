# 复盘 03：用事故数据修正熔断器设计

## 背景

小戴能修改自己的部分组件。为了防止它在状态不好时把自己改坏，我们给“高风险改动”加了熔断器，最初有两个触发条件：

- **条件 A：全局负载过高时拒绝高风险改动**
- **条件 B：短时间内连续多次高风险改动时拒绝**

负载按加权方式计算，熔断器带滞回：超过上限触发，回落到更低的阈值才恢复，避免在临界点来回抖动。

## 事故

一次事故中，系统在修改消息中继时把中继改坏了。直觉上会怀疑是负载过高。我们用历史记录回放了当时的负载曲线，结果发现：

**出事那一刻的全局负载很低。**

真正的特征是：在那之前，系统已经对同一区域连续做了好几次改动。

## 结论

- 条件 B（连续改动检测）才是能拦住这次事故的那一条。
- 条件 A 在这个场景下不会触发。我们原本为它设计的一套细分负载统计，事后证明并没有提供额外价值，于是删掉了。
- 闭环状态机保留硬中止入口；配套的重启限制协议堵住了 agent 自我认证“已经恢复”的漏洞。

## 收获

**熔断器的规则要用真实事故去验证，而不是靠直觉。**我们靠的是动作日志和转录回放：每一次主 agent 的写入和命令都有记录，子 agent 交接也有记录，所以事后能还原出准确的时间线。
